# Design: Execution HTTP/domain contracts

## API shape

The service exposes execution-owned task resources under `/execution-tasks`:

- `POST /execution-tasks` creates or idempotently returns a queued task.
- `GET /execution-tasks/{taskId}` returns the persisted task.
- `PATCH /execution-tasks/{taskId}/status` advances task status.

Task identifiers are generated by the Execution Service. Callers may provide `X-Correlation-Id` for traceability and `Idempotency-Key` for safe retries. The create response returns HTTP 201 for a new task and HTTP 200 when the same idempotency key maps to an existing task.

## Domain model

An execution task stores `taskId`, `workflowId`, `input`, `status`, optional `result`, optional `errorMessage`, optional `correlationId`, optional `idempotencyKey`, and timestamps. Status values are `queued`, `running`, `completed`, and `failed`.

Allowed transitions are:

- `queued` -> `running`
- `queued` -> `failed`
- `running` -> `completed`
- `running` -> `failed`

Terminal statuses cannot transition further.

## Persistence boundary

The HTTP layer depends on the existing MongoDB repository boundary. The repository remains responsible for mapping MongoDB documents to domain records, creating unique indexes, looking up tasks by task ID, looking up idempotent creates by idempotency key, and persisting status details.

## Validation

The route layer performs minimal JSON contract validation without adding extra runtime dependencies. Invalid JSON, invalid fields, missing required fields, unsupported status transitions, and missing tasks return structured JSON error responses.

## Deferred work

RabbitMQ event consumption/publication and saga orchestration are intentionally deferred to `f4-execution-rabbitmq-events` and later integration changes.
